Featured project: SatornTCG AI Assistant

An MCP server that lets an AI assistant work against the live data of a real trading-card resale business, built with the observability, testing, and access controls I'd expect of an enterprise platform.

In daily use

satorntcg-mcpserver

The problem

Running a resale business means constant questions: what's underpriced, which box paid off, which orders still need listings. Answering them meant clicking through dashboards. This server exposes the business's inventory, pricing, P&L, and order data as standardized tools, so an assistant like Claude can answer from live data instead of a demo set.

Architecture

Key engineering

  • MCP tool layer — 11 tools covering inventory, pricing, box and business P&L, eBay listings, TCGplayer order sync, and eBay deal scanning, each published with a JSON input schema for discovery and execution.
  • Validated, bounded queries — server-side argument validation with filtering, sorting, and hard row limits, since the low-level MCP server doesn't enforce schemas itself.
  • Agent runner with guardrails — a CLI agent on the Claude API that offers only read-only tools, checks every argument against the tool's schema before calling it, and stops after 5 tool rounds.
  • Resilient integrations — bounded retries with jittered backoff for idempotent HTTP reads only. Write calls never retry.

Testing & observability

  • 78 automated tests passing (Node test runner): argument validation, an MCP integration test that starts the real server and checks tool discovery, agent loop logic, retry behavior, and telemetry export.
  • LLM evaluations — a live Claude API eval checks tool selection and arguments for natural-language questions, and checks that the model answers directly, asks for clarification, or declines when no tool fits. Repeat runs measure consistency.
  • Distributed tracing — every tool call is a span with each database query as a child span, so slow calls are flagged automatically and you can see whether time went to the database or the handler. Trace context is passed from agent to server through MCP request metadata, so one trace covers the whole request.
  • Metrics — request, tool-call, latency, and token-usage metrics through an OpenTelemetry Collector into Prometheus and Grafana. Labels are kept to an allowlist, so prompts and data never end up in metric labels.

AI security & observability

An agent that can query and change business data is a platform like any other: it needs access control, monitoring, and regression testing. What's built and what's next:

Built in SatornTCG Implemented

  • Least-privilege tool access — the agent gets an allowlist of read-only tools, and any other tool request is rejected before it reaches the server.
  • Input validation at two layers: schema checks in the agent, plus validation and row limits on the server.
  • Data protection in telemetry — agent traces and metrics leave out prompts, message content, tool results, and credentials, and a test confirms retry telemetry never records headers.
  • Secrets handling — credentials stay in local environment files and out of source control. The web app uses Postgres row-level security across all its views.
  • Tracing and tool monitoring, with slow tool calls flagged automatically.
  • Evals as regression tests for tool selection and refusal behavior.

Studying & planned Not yet built

  • Human approval enforced on the server for tools that write data, rather than relying on the client's confirmation prompt.
  • Prompt-injection defenses for tool results that contain untrusted third-party text, such as marketplace listing titles.
  • Authentication and per-user authorization for remote MCP access.
  • Audit logging and governance — a durable record of who triggered which agent action, and why.
